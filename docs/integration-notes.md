# Persona Weaver: проверенные интеграции

Дата: 4 ноября 2026 года. Проверено по установленному исходному коду SillyTavern. Адаптер реализован в `index.js`; полный путь проверен на изолированном браузерном стенде. Реальные провайдеры и пользовательские книги в проверках не использовались.

## Контекст и сообщения

| Задача | Проверенный источник |
|---|---|
| Активная персона | `scripts/personas.js`: экспорт `user_avatar`; описание в `power_user.persona_descriptions` |
| Чат и сообщения | `SillyTavern.getContext()`: `chat`, `chatMetadata`, `getCurrentChatId()`, `characterId`, `groupId` |
| Стабильность при переименовании | `chatMetadata.integrity`, а не отображаемое название файла |
| Различение владельцев | Аватар карточки персонажа или ID группы; числовой индекс карточки не использовать как постоянный идентификатор |
| Ветка | `scripts/bookmarks.js:createBranch()` создаёт новую `integrity` |
| Скрытые сообщения | `is_system`; по умолчанию пропускать, включать только явно |
| Изменённый вариант | `mes` и `swipe_id`; перед применением сверять снимок источников |
| События | `CHAT_CHANGED`, `PERSONA_CHANGED`, `MESSAGE_SWIPED`; сверка контекста после каждого асинхронного шага обязательна независимо от событий |

Составной идентификатор: персона + владелец чата + integrity. При отсутствующей integrity анализ не запускается. Для старых чатов нельзя придумывать новый ID на каждом открытии.

Важно: `getOrCreatePersonaDescriptor()` имеет побочный эффект создания описателя. Для простого чтения достаточно существующих полей `power_user`.

При создании ветки `saveChat()` объединяет старые метаданные с новыми. Журнал анализа должен различать новую integrity и исходную ветку. При этом накопленный канон остаётся в одной книге персоны, а метки сохраняют исходное происхождение сведений.

## Один лорбук и метки принадлежности

Актуальное решение пользователя: одна книга, привязанная к персоне. Метки «Общее» и «Из чата: название» помогают организовать записи, но не фильтруют их попадание в контекст. Отдельная книга текущего РП не создаётся.

Используем штатную привязку персоны через `power_user.persona_description_lorebook` и описатель персоны. Активация записей остаётся штатной: ключи, постоянная активация, бюджет и остальные настройки World Info. Расширение не выключает записи ради изоляции и не перехватывает `WORLDINFO_ENTRIES_LOADED` для ограничения канона по чату.

В служебных данных хранятся принадлежность и источники отдельных добавлений. Один тематический раздел может содержать сведения из разных чатов и общие сведения. Обновление не должно затирать прежние метки. Точные поля метаданных определить при реализации; названия чатов служат подписями, стабильные идентификаторы — ссылками.

Прежняя функция `scopedEntry()` удалена. Метки реализованы через `personaCanon.origins`: каждый принятый фрагмент сохраняет вид метки, идентификатор контекста, подпись чата, дату и подтверждающие цитаты. Активация остаётся штатной.

## Запрос к модели

`ConnectionManagerRequestService.sendRequest(profileId, prompt, maxTokens, custom, overridePayload)` поддерживает выбранный профиль подключения, массив сообщений и `AbortSignal` через `custom.signal`.

Непотоковый извлечённый результат имеет поля `content` и `reasoning`. Анализировать нужно `content`. Ошибка профиля не должна приводить к скрытому переключению на другое подключение.

Дополнение после одобрения макета: первая версия должна поддерживать три режима — текущее подключение, выбранный профиль и отдельный API с загрузкой моделей / ручным вводом. Подробные требования находятся в разделах 8.1 и 8.2 плана. Ограничение первой интеграции только профилем больше не применяется.

В локальном BB Enhance проверены `generationSource`, `connectionProfileId`, отдельные URL/ключ/модель, кнопка обновления моделей и ручной ввод модели. Это референс интерфейса, не доказательство совместимости выбранного адаптера. Поддержку обоих типов профилей нужно проверить отдельно; нельзя передавать массив chat-сообщений в текстовый API без корректного преобразования.

`getTokenCountAsync()` доступен через контекст. Оценка размера запроса выполняется после сборки полного входа, а не только по выделенной сцене.

Контракт ответа определён в `core.mjs:validateSuggestions()`. Приложение назначает метку принадлежности, владельца, авторство и статус; модель их не контролирует. Совпадение цитаты подтверждает наличие источника, но не истинность вывода — проверка пользователем остаётся обязательной.

## Сохранение и очередь

`loadWorldInfo()` может возвращать кэш. Для проверки актуальности непосредственно перед записью нужен свежий запрос `/api/worldinfo/get` с `getRequestHeaders()`.

`saveWorldInfo()` обновляет кэш до завершения запроса, а его внутренняя `_save()` не проверяет `response.ok`. Поэтому успешный `await saveWorldInfo()` сам по себе не доказывает сохранение.

Адаптер записи должен:

1. Получить свежую книгу и проверить текущий контекст, базовую версию целевой записи и источники.
2. Изменить копию книги, сохранив все чужие поля и записи.
3. Отправить `/api/worldinfo/edit` и проверить статус и `{ ok: true }`.
4. После успеха обновить экспортированный `worldInfoCache` и уведомить через `WORLDINFO_UPDATED`.
5. Сохранить результат по каждой записи и снимок для отката.

Сервер записывает книгу целиком и не предоставляет compare-and-swap. Сверка перед сохранением уменьшает риск, но не гарантирует защиту от одновременной записи из двух вкладок. Не обещать атомарность пакета или полную защиту от параллельного внешнего редактора.

Очередь и история реализованы в IndexedDB вместо первоначально рассмотренного `accountStorage`: это позволяет дождаться локальной транзакции и не раздувать настройки ST полными сценами. Ключ включает учётную запись ST и составной идентификатор контекста. Перед HTTP-записью сохраняется намерение со снимками до/после; после подтверждения — результат. Незавершённую операцию можно сверить и продолжить без повторного создания записи. Данные локальны для браузера. При превышении 10 млн символов на контекст запись останавливается без удаления истории; экспорт доступен в интерфейсе.

Ключ отдельного API хранится только в памяти страницы. URL/модель и остальные настройки сохраняются отдельно в `extensionSettings`. Встроенное хранилище секретов ST не изменяется, активные ключи основного подключения не переключаются. Отдельный API использует прямой браузерный запрос и требует CORS. Текстовые профили проходят через `ConnectionManagerRequestService.constructPrompt()`.

Журнал анализа — отдельная сущность от истории применения. Он хранит покрытие диапазонов и снимки/отпечатки источников, распознаёт повторные и пересекающиеся сцены. Успешный пустой результат тоже покрывает диапазон; ошибка запроса — нет. Статус применения предложений на покрытие не влияет. Хранить только последний обработанный номер сообщения недостаточно.

## Проверки и оставшиеся ограничения

- Выбрана одна книга, действительно привязанная к нужной персоне.
- Метки принадлежности и фильтр списка не меняют штатную активацию записи.
- Пополнение раздела из другого чата сохраняет все источники и метки.
- Ключи, бюджет и позиция вставки работают штатно.
- После отключения расширения записи продолжают работать как обычные записи лорбука.
- Ошибка записи не отмечается как успех и не загрязняет кэш.
- Смена контекста во время анализа не переносит предложения в другой чат.

31 проверка логики и изолированный сценарий браузера пройдены. Браузер загружает реальные `index.js` и UI расширения, но API/модули ST подменены стендом. Проверена доступность manifest/JS/MJS/CSS через работающий ST на localhost. Реальное включение по ключам в промпт конкретной пользовательской истории и совместимость с конкретным провайдером требуют пользовательского прогона. Механизм World Info не переопределялся.
